## 〇、【补记】第二个报错 `cfg is not defined` —— 我自己引入的回归

### 现场

用户第二次点「画一张」报：`cfg is not defined`。

### 根因 —— **就是我在修 `[object Object]` 时改坏的**

为了给 `execute()` 加一层"错误规范化"，我把 `makeDrawTool` 里的 `execute` 函数体
**原样搬成了顶层函数** `runDraw(args, exec)`。但函数体里引用的
`cfg` / `log` / `onProduced` / `onStart` **本来是 `makeDrawTool` 的闭包变量** ——
搬出去之后**全部丢了作用域**。`runDraw` 体里 `cfg` 被引用 **17 次**、`log` **10 次**，
第一处 `cfg.imageBackend` 当场抛 `ReferenceError: cfg is not defined`。

### 为什么之前的 12 个测试全绿却没发现

因为**自由变量在语法上是合法的** —— `node --check` 查不出来，
而我那些测试全是"调纯函数"，**从来没真的执行过 `execute` 这条路径**。

### 修法

```js
// execute 里：把四个闭包变量**显式**传下去
return await runDraw(args, exec, { cfg, log, onProduced, onStart })

// runDraw 签名：接住它们，并加一道守卫
async function runDraw(args, exec, deps) {
  const { cfg, log, onProduced, onStart } = deps ?? {}
  if (!cfg || typeof log !== 'function') {
    throw new Error('插件内部错误：出图逻辑缺少必需依赖（cfg / log）。这是插件的 bug，请重载插件后重试。')
  }
```

### 验证：不再靠猜，直接跑一遍

新增 `scripts/_draw_smoke_test.mjs` —— **真的调用 `execute()`**，
把 `comfyUrl` 指向必连不上的端口、`autoStartComfy: false`，然后断言**失败原因**：

```
OK   ① execute 抛出了错误（而不是静默返回）
OK   ① 不是 ReferenceError（cfg/log 等没丢）
       — 连不上本机 ComfyUI（http://127.0.0.1:59999）：fetch failed
OK   ① 抛的是真正的 Error 实例
OK   ① 失败原因是"连不上 ComfyUI"（说明依赖齐全、走到探活了）
OK   ② execute 内部确实把 deps 传下去了
OK   ③ 空 prompt 抛出 Error / 报的是人话
OK   ④ 工具定义完整（name/description/parameters/execute/planWorkflow）
```

**并反向验证过这个测试真的有牙**：复制一份 `index.js`、把 `deps` 去掉做成坏版本，
对副本跑同样的调用 —— 坏版本抛出的正是：

```
cfg is not defined        ← 与用户报的一字不差
```

### ★ 一个大教训：别手写 JS 词法分析器

我先是写了个静态"符号解析"检查器想兜住这类 bug，结果踩了更大的坑：

`safeStem()` 里有一行正则字面量 `/[\\/:*?"<>|\r\n\t]+/gu` ——
**字符类里含双引号**。手写 stripper 不认正则字面量，一看到 `"` 就当成字符串开头，
从此再也出不来 → **后面 28 个顶层函数全被吞掉**，误报一片。

JS 的词法歧义（除号 vs 正则、模板嵌套、正则里的引号）**不是正则能搞定的**，
必须上真解析器。为一条自测引入依赖不值当 ——
**所以放弃静态方案，改用"真跑一遍"的端到端冒烟测试。** 已删掉那个坏掉的检查器。

## 〇·五、【最新】生图意图判定调优 —— 让助手**不再绕过插件自己画**

### 现场（用户原话）

> 「我不是让你用插件出图吗？为什么你自己再画呀… 我让他画图，为什么他还想自行代码画
> 你把这个插件的判断调优一下。」

具体经过：用户说「画一幅表现双曲几何之美的数学艺术画」，助手**根本没调 `draw_image`**，
而是自己写 Python/Matplotlib 渲染了一张 —— 耗时 **2 分 39 秒**，出完还附赠一通
「数学上不精确」「要不要我改用代码画 / 放大 / 换配色」的分析。

### 根因 —— 两处，都在我写的提示词里

**① 判定标准用错了维度：拿"题材"当判据。**

旧文案的排除清单是「流程图 / 思维导图 / 表格 / 架构图 / **示意图**」。
「示意图」这三个字是个万金油：助手看到"数学 / 几何 / 可视化"，就往"图表类"上靠，
于是判定"这不是画图工具的活儿" → 不敢调。

**② 全篇没有任何一条"禁止助手自己用代码出图"的硬约束。**

这是致命的那一条。旧文案只在劝退方向上下了功夫（「宁可先问一句，也不要画错」），
却**没有堵住另一条路** —— 助手"不敢调工具"之后的自然选择就是自己动手，
它还会自我合理化：觉得代码渲染"更精确、更可控"。
结果就是：用户觉得"傻"，而且比画错更糟 —— 画错重画只要十几秒，自己画要 2 分 39 秒。

### 修法（三处，逐个对着根因）

**① 判定标准从"题材"换成"产物形态"**

问的不是"这属于什么领域"，而是：

> 用户要的是**一张位图**，还是**能改文字 / 改数据的结构化图表**？

题材（艺术、插画、壁纸、概念图、数学、几何、物理）**一律不影响归属**。
并把这句写进提示词：「题材完全不影响判断」。

**② 排除清单收窄，删掉"示意图"**

只剩明确的、可编辑的那四类：流程图、思维导图、组织架构图、数据表格。

**③ 新增四档共通的「不许自己画」铁律（`NO_SELF_DRAW_RULE`）**

单独抽成常量、**四档全部注入**（不是只在 `auto` 里补一句 ——
因为这不是某一档的措辞问题，是任何一档都缺这条底线）。措辞写成**禁止 + 理由**：

```
★ 不许自己"画"图：不要写 Python/Matplotlib/PIL、SVG、HTML/Canvas、Mermaid 或字符画
  去生成用户要的那张图。出图只能通过 draw_image —— 绕过它自己去渲染属于错误行为。
  （哪怕你觉得代码渲染"更精确/更可控"也不行：用户装这个插件就是为了用它出图。）
★ 别自作主张改需求：不要因为"模型画的数学不精确"就擅自换成代码渲染，
  也不要在出图后附加"要不要我改用代码画""要不要放大/换配色"这类追加方案 ——
  先把图给用户，等用户开口再说。
```

后半段专治那次事故里的"出完图还追着给 a/b/c 选项"。

**④ 工具描述（`draw_image.description`）同步改**

工具描述是模型**最先**看到的信息，比 systemPrompt 段落更靠近"要不要调这个工具"的那一刻，
所以边界必须写在这里：

- 「只要用户要的是**一张图像**（……数学/几何可视化等，题材不限），就用本工具生成。」
- 「★ 严禁自己写 Python/Matplotlib/PIL、SVG、HTML/Canvas 或字符画去"画"这张图 ——
  本工具就是用来出图的**唯一途径**。」
- 「拿不准就调本工具画一张（画错代价远小于不画或自己画）。」

**⑤ 把"宁可先问一句"改成"拿不准就画一张"**

实测下来的代价排序是：**自己写代码画（最糟） > 不画先问（烦） > 画错（重画即可）**。
旧文案押的是反的那一头。

## 〇·六、【最新】出图耗时取证 —— 80 秒到底花在哪

> 用户问：「我打那么多优化，主要那点时间为什么工作流耗费这么长的时间」。
> 我不再猜，直接把 ComfyUI 日志里 6 笔真实出图逐笔拆开算账。
> **详见配套报告 `出图耗时-取证与优化报告.md`。**

### 结论（一句话）

**80 秒里只有 45 秒在"画画"，35 秒（43.5%）在把 13.58 GB 模型重新搬进显存。
而同样的图，模型只要已经在显存里，就只要 23 秒。**

### 关键数据

| # | 采样s | 总s | 非采样s | 非采样% | 加载MB |
|---|---|---|---|---|---|
| 3 | 15.0 | **23.00** | 8.00 | 34.8% | **644**（模型已驻留） |
| 6 | 45.0 | **79.70** | 34.70 | 43.5% | **13584**（全量重搬） |

平均非采样开销 **30.49 s，占 38.4%**。同样 8 步，单步耗时在 **1.88 ~ 15.50 s** 之间波动 8 倍。

### 排除了一个错误方向

`To see the GUI go to` / `Total VRAM` 各只出现 **1 次** ⇒ ComfyUI 全程只启动一次，
**这不是冷启动问题**，是模型在进程存活期间被反复卸载。

### ★ 推翻了之前一份报告的结论

日志原句：`Qwen TE predictor: predicted 0/8 steps (0.0% model-call acceleration)`。

`叠加加速方案实测报告.md` 里 TE+Speedup 有 +25.4%（11.581 s → 8.639 s），
但那是**模型已驻留 + 较小尺寸**的理想条件。在 1408×1408 的真实场景里 **TE 是 0%**、
Speedup 只有 12.5%。

> ⇒ **那些加速方案的收益高度依赖"模型有没有常驻"，这一点原报告没写。**
>    这就是用户"打了优化却没感觉快"的真正原因：优化的是那 8 步，而大头不在那 8 步。

### 本轮改动

- `--reserve-vram` **1.5 → 0.5**：把 1 GB 还给模型/激活，争取让 13.58 GB 常驻。
  （19.98 GB − 13.58 GB 模型 − 1.5 保留 = 只有 4.9 GB 给激活 ⇒ 换页。）
- 面板文案同步改成 0.5（两处写死同一数值，有断言钉死，防止假报告）。
- 新增 `scripts/_timing_forensics.py`（已进包），以后随时可自行复算耗时分解。

**⚠ 启动参数改动必须重启 ComfyUI 才生效，且我在沙箱里无法实测 —— 不假报成功，

## 〇·七、【最新】wrapper 三选一按出图尺寸自动切换 —— 把"1408 能用的可叠加优化"加回来

### 用户原话
> 在 1408×1408 的真实场景里 TE 是 0% …… 之前那么多弃用的方案可以添加进去了呀，
> 你找一个在 1408 乘 1408 里能用的优化方案。就是可以叠加的。

### 现场（被实测推翻的旧结论）
上一轮我把 `blockCacheEnabled=false` 关掉了 BlockCache T8，理由是「小尺寸 + 模型已驻留」下
TE+Speedup（8.639 s）< BlockCache（9.712 s）。但那个对比是**理想条件**：

- **1408×1408 才是用户真实在用的尺寸**。该尺寸 ComfyUI 日志白纸黑字：
  `Qwen TE predictor: predicted 0/8 steps (0.0% model-call acceleration)`、
  `QwenImage21Speedup: 1 cached of 8 (12.5% skipped)` ——
  TE 一步都没命中、Speedup 只跳 1 步，却**独占着 wrapper 坑**。
- BlockCache T8 大尺寸实测 **+22.7%**（120.75 s → 93.34 s，省 27.4 s），且官方描述
  "preserving Core's reference/text KV cache" ⇒ **原生兼容前缀缓存**，能跟 turbo8 + 前缀 KV 缓存**叠着用**。

⇒ 用「一套配置硬扛所有尺寸」必然有一档是错的。

### 修法（按尺寸二次决策，不再静态一刀切）
- 新增 `pickWrapperSet(cfg, plan, width, height, caps)`：用 **latent token 数** `round(W/8) × round(H/8)` 分档。
  - 小尺寸（≤ 16384 tokens，即约 1024² 及以下，如 992²=15376）→ **TE-Speed + Speedup**（小尺寸实测 +25.4%）。
  - 大尺寸（> 16384，如 1408²=30976）→ **BlockCache T8**（大尺寸实测 +22.7%）。
- `blockCacheEnabled` 从 `false` **翻回 `true`**（auto 模式要让大尺寸能上 BC）。
- 新增 `DEFAULTS`：`wrapperPolicy: 'auto'`（可选 `te` / `bc` 强制某一套）、`wrapperAutoTokensThreshold: 16384`。
- `buildWorkflow` 改读 `wrapperPick` 的 `te / speedup / blockCache`，**互斥由函数硬保证**
  （BlockCache 上时 TE/Speedup 必为 false，否则同挂 `DIFFUSION_MODEL` wrapper 会 `ValueError` 整单失败）。
- 面板新增「互斥三选一策略（wrapper）」项，如实说明当前档位与分界；TE/Speedup 让位关系改成"按尺寸让位"。

### 验证
- `scripts/_wrapper_policy_test.mjs`（已进包）：auto/te/bc、尺寸边界（1032² 越阈→BlockCache）、
  互斥（BlockCache 上时 te/speedup 必 false）、能力缺失回退（大尺寸无 BC 节点→退回 TE+Speedup）全绿。
- `scripts/_wf_wrapper_integration.mjs`（**新增**，已进包）：直接调 `buildWorkflow` 验证节点接线——
  992² 挂 TE(13)+Speedup(14)、1408² 挂 BlockCache(16) 且 turbo8 LoRA + 前缀缓存(7) 仍保留（可叠加）、
  大尺寸无 BC 节点→退回 TE+Speedup，全绿。
- `scripts/_opt_status_test.mjs` 同步更新到新结构（7 项明细、BlockCache 默认 on），全绿。

**⚠ 与上一轮一样：wrapper 切换发生在出图时，沙箱里无法真跑 ComfyUI，

## 〇·八、【最新】隐患排查：修掉一个**我自己引入的可见回归**（面板显示"未确认"）

改完 〇·七 后我没有直接收工，而是把新链路从头到尾又排查了一遍，结果真查出一个
**我这次改动直接放大**的 bug —— 属于"代码逻辑对、但界面说谎"，正是要严防的假报告。

### bug：`superseded` 态在前端**没有档位**，被兜底渲染成"?"未确认

- 前端 `lib/client.js` 的 `OPT_STATE_VIEW` 只有五档：`on / available / off / blocked / unknown`；
  取值走 `OPT_STATE_VIEW[key] ?? OPT_STATE_VIEW.unknown` —— **缺档即兜底成 unknown**。
- host 侧 `superseded`（按尺寸让位）这一态**早就有了**，但以前 `blockCacheEnabled` 默认为 `false`
  ⇒ `plan.useBlockCache` 恒 false ⇒ 这一态**根本不会出现**，缺档也就一直没暴露。
- 〇·七 把 `blockCacheEnabled` 翻成 `true` 后，**TE-Speed 与 Speedup 默认就变成 `superseded`** ——
  于是它们会被渲染成 **`? 未确认`**（灰色）⇒ 把"已知且正常"说成"未确认"。这是可见回归。

### 修法
- `OPT_STATE_VIEW` 补 `superseded` 档：`mark: '⇄'`、`label: '让位（按尺寸）'`、独立配色 `qwen-paint-opt-sup`（蓝）。
  保持"**颜色 + 字形**"双通道（⇄ 与 ✓ / ✕ / ? 都不同，色觉障碍用户也能区分）。
- 面板 summary 同步改尺寸感知：原来无条件写 `+ BlockCache`、`N 项让位于 BlockCache` ——
  现在 auto 档写成 `+ wrapper 按尺寸自动（小尺寸 TE+Speedup / 大尺寸 BlockCache T8）`、`N 项按尺寸让位`。
- 测试加锁：`_opt_status_test.mjs` 断言渲染表**必须含全部 6 档**（缺档会兜底成 unknown）、
  superseded 有独立配色与字形、三种 `wrapperPolicy` 的 summary 各自如实点名。

### 排查中确认**不是** bug 的两处（如实记录，不虚报）

1. **图生图尺寸不一致？** 不是。img2img 的 latent 来自节点 5（`latent_image: ['5', 2]`），
   而节点 5 的 `resolution = sqrt(effWidth×effHeight)` —— **输出尺寸由 effWidth/effHeight 驱动**
   （参考图被缩放适配），与 `pickWrapperSet` 用的尺寸是同一个，判定一致。
2. **探测失败会挂上没装的 BlockCache 节点吗？** 不会。`probeCapabilities` 失败时把 `level` 设成 `'full'`，

## 〇·十五、【最新】"拉起后端自动最小化"一直不生效 —— 真根因（Windows Terminal）

用户反馈：「那个拉起后端的最小化，怎么还没有（做）？」——**之前实现过、但一直没生效**。
这次查到了真根因，不是没写，是**写的方式在 Win11 默认终端下必然失效**。

### 现场取证
- 启动脚本 `X:\ComfyUI\.dshqp-launch.cmd` 确实存在，里面用
  `start "" /b powershell -File .dshqp-minwin.ps1` 去最小化控制台窗口；`.ps1` 也确实生成了。
- `DSHQP_NOMIN` **未设置**（不是逃生门被触发）。
- 机器上跑着 **Windows Terminal**（pid 14856，标题 `C:\WINDOWS\system32\cmd.exe`）+ `OpenConsole`。

### 真根因
`.ps1` 的第一步是 `GetConsoleWindow()` 拿"自己的控制台窗口"，只要**非零就直接用它**。
但在 **Windows Terminal** 下，`GetConsoleWindow()` 返回的是 **`PseudoConsoleWindow`（不可见的伪控制台）**——
对它 `ShowWindow(hwnd, 6)` **没有任何可见效果**。
更糟的是：因为 `$own` 非零，脚本里"按 `ConsoleWindowClass` / `CASCADIA_HOSTING_WINDOW_CLASS` 找窗口"的
**兜底分支根本不会执行** ⇒ **永远什么都没最小化**。（旧脚本还把输出全 `>nul` 吞了，所以一直"看起来像做了"。）

### 修法
1. **顺序反过来：优先找"可见"的窗口** ——
   ① 按**唯一标题**（`.cmd` 里新增 `title DSHQP-ComfyUI`）→ ② 可见的 Windows Terminal 窗口
   → ③ 可见的传统控制台窗口 → ④ **最后**才用自身控制台，且**要求它可见**。
2. **结果落盘**到 `.dshqp-minwin.log`（`hwnd / 命中方式 / 窗口类名`）——旧脚本全吞了，出问题完全看不到。
3. `.cmd` 里加 `title DSHQP-ComfyUI`：既供按标题精确定位，任务栏里也显示成人看得懂的名字。

### 验证（我看不到屏幕，所以做了能做的静态验证）

  若仍不行，把 `.dshqp-minwin.log` 的最后一行发我（它会写明找到了哪个窗口、用什么方式）。

## 一、修掉了「画图失败：Error: [object Object]」—— 真根因

### 症状
点「画一张」，工具回报一句：

```
画图失败：Error: [object Object]
```

**信息量为零**：不知道哪一步失败、为什么失败。用户只能干瞪眼。

### 根因（已实测复现，不是推测）

`AbortController.abort(reason)` 会把 `reason` **原样**变成 `fetch` 的 reject 值。
实测四种 reason 的落地形态（脚本：`scripts/_abort_reason_test.mjs`）：

| 传给 `abort()` 的东西 | fetch 最终 reject 出的值 | `String(e)` 的结果 |
|---|---|---|
| `new Error('x')` | 同一个 Error | `Error: x` ✅ |
| **普通对象 `{...}`** | **同一个普通对象** | **`[object Object]`** ❌ |
| 字符串 `'x'` | 同一个字符串 | `x` ⚠ |
| `undefined` | DOMException | `AbortError: …` ✅ |

而 **DSH 宿主传进来的 `exec.signal.reason` 就是普通对象**（不是 Error）。
老代码干的是：

```js
const onAbort = () => controller.abort(signal.reason)   // ← 原样转发
```

于是宿主那个普通对象被当成 abort reason 一路传上去，宿主 `String()` 之后
就成了用户看到的 `[object Object]`，**把真实原因全糊掉了**。

### 修法（三层防线）

1. **新增 `toError(value)`** —— 任何形态的输入都能得到一个带可读 message 的 `Error`。
   普通对象会优先掏它身上的 `message` / `msg` / `reason` / `error` / `detail` 字段，
   掏不到再退到 JSON（截断 500 字符），最后兜底一句中文。
2. **新增 `cancelReason(signal)`** —— 把外来 `signal.reason` **翻译成人话**，
   **绝不原样转发**。四种调用点全部改用它：
   - `fetchWithTimeout` 里的 `controller.abort(...)`
   - 参考图上传里的 `controller.abort(...)`
   - 两处 `throw signal.reason` → `throw cancelReason(signal)`
3. **`execute()` 外层包一层规范化** —— 真正的逻辑搬进 `runDraw()`，
   `execute` 只负责 `try { runDraw } catch { 非 Error 就 toError 再抛 }`。
   这样**无论哪里漏出来**，用户看到的都是人话。

### 验证（`scripts/_abort_fix_test.mjs`，已进包）

```
Error 实例               → ✅ Error: 用户取消
普通对象(带message)         → ✅ Error: 任务已取消：宿主中止
普通对象(带code)            → ✅ Error: 任务已取消：取消了
普通对象(空)                → ✅ Error: 任务已取消（宿主中止了这次调用）
字符串                    → ✅ Error: 任务已取消：aborted
null / undefined / 数组   → ✅ Error: 任务已取消（宿主中止了这次调用）

结果：通过（无 [object Object] 泄漏）
```

## 二、BlockCache T8 做成**真开关**（用户可自行开关）

### 问题
原先面板里 BlockCache T8 那一项**只显示调参说明，没有任何开关**；
而它与 TE-Speed / Speedup 三者结构互斥（只能一组生效），用户却没法自己切。

### 做法

**host 侧**（`lib/index.js`）
- 新增 `?blockcache=on|off` 处理分支（跟既有的 `?start=1`、`?idleMinutes=N` 同一套约定）。
  改的是内存里的 `cfg.blockCacheEnabled`，**当场生效**，不需要重启 ComfyUI。
- `describeOptimization` 的 `item()` 构造函数新增可选 `toggle` 字段：
  ```js
  toggle: { key: 'blockcache', on: <当前开关>, canToggle: <装了节点才可切>, hint: '<一句说明>' }
  ```
  只有 BlockCache 这一项挂了 `toggle`，其他项不受影响。

**client 侧**（`lib/client.js`）
- 那一行下面渲染一个标准 `role="switch"` 胶囊开关：开=绿、关=灰、缺节点=置灰不可点。
- 点击 → `fetch('api/qwen-paint/status.json?blockcache=on|off')`
  → 调 `onToggleDone` 立刻重拉状态（不等下一次 5 秒轮询）。
- ⚠ 点击处 `event.stopPropagation()`：面板外面有「点空白处关闭」的 capture 监听，
  不拦的话点开关会顺手把整个面板关掉。

### 诚实边界（重要）

这是**运行时开关**：`blockCacheEnabled` 是内存态，**DSH 重载后会回到配置文件的值**。
所以开关下面**明确写着**：

> 即时生效；要永久保存：在这台机器的 cordis.patch.yml 里把 blockCacheEnabled 写成
> true/false，重启 DSH 后依然保留。

没有把插件做成"偷偷改配置文件"——插件拿不到自己配置文件的可靠路径
（DSH 的 profile 路径因安装方式而异），盲写文件的风险远大于收益。
