# 「界面一直卡在正在启动中」—— 根因定位与修复

更新时间：2026-10-09 13:3x（第二版，含实锤证据）
影响文件：`lib/index.js`（后端 host）+ `lib/client.js`（前端界面）

## 一、结论（已用 A/B 测试坐实，不是推测）

**根因：初始化过程中 `ctx.on(...)` 是一次裸调用，在你的宿主上 `ctx.on` 不是函数，
抛出的 `TypeError` 没有被捕获，把整个初始化回调掐死了 —— 排在它后面的「状态端点注册」因此从未执行。**

前端每次轮询 `/api/qwen-paint/status.json` 都拿不到数据，`startingNow` 再也没人更新 →
按钮**永远显示「正在启动…」**。

**出图功能不受影响**（工具注册排在 `ctx.on` 之前，已经完成了）。

> 一句话：不是"启动慢"，不是"状态机写错"，是**一次未捕获的异常掐断了初始化链**。

- **宿主能力快照**：`[host] ctx API：on=? effect=? inject=? get=? tools=? webServer=?`
  —— 一次看清宿主给了什么，彻底终结"猜宿主"。
- **步骤级诊断**：每个 step 都写 `[init] xxx OK` / `[init] xxx 失败：原因`。

### 2. `lib/client.js` —— 给本地「启动中」加兜底收口

**效果**：即使后端还有别的毛病，界面也**绝不再无限显示「正在启动…」**，

8 条新断言，专门盯"宿主 API 裸调用"这个坑：

## 七、第二轮修复（2026-10-09 13:5x）：又抓到两个真凶

重启后菜单能显示了（说明 client 半边已加载、`bundles` 那步是对的），但「正在启动…」**还是卡**。
新日志给出了决定性证据：

```
[apply] 插件开始加载 pid=19592
[inject] 准备注册 root.inject([tools, sessionProjections])
        ← 到此为止！**没有 [host]**，说明 root.inject 的回调从未执行
```

### 真凶 A：`root.inject` 的依赖没满足 → 回调被静默挂起

`root.inject(['tools', 'sessionProjections'], cb)` 把 **`sessionProjections` 列为必需依赖**，
但它在本插件里**只用于一个 try/catch 内的可选查询**（取 turn boundary，取不到就跳过）。
cordis 的 inject 在依赖未满足时**不报错、不执行** —— 于是工具、状态端点、提示词全都注册不上。

**修法**：依赖收窄为 `['tools']`，`sessionProjections` 改成**可选获取**
（`ctx.sessionProjections ?? ctx.get?.('sessionProjections')`），
并在 `[host]` 快照里记录它是否存在。另加 **8 秒兜底回看**：回调若仍未执行就明确落盘。

### 真凶 B：状态接口抛错时，返回的响应**没有 `online`/`starting` 字段**

handler 的 catch 以前只回 `{ ok:false, reason }`。而前端 `startingNow` **只在**
`typeof data.starting === 'boolean'` 时才更新 —— 于是 handler 一抛错，前端就**永远收不到状态**，
`startingNow` 卡在 true，界面永久停在「正在启动…」。

**修法**：catch 里 ① 落盘原因（`diag('status')`，以前完全静默）；
② **带上 `online/starting/launchFailed` 字段**，让前端把"启动中"收掉
（宁可显示"未就绪"，也不能假装在启动）。

### 真凶 C（前端）：兜底收口只覆盖了"点按钮"这一种来源

上一版只在点启动按钮时计时（`startRequestedAt` 由 `startComfy` 设置），
而后端也能把 `startingNow` 设为 true —— 那种情况计时起点是 0，**收口条件永不成立**。
**修法**：只要 `startingNow` 为 true（不管谁设的），就从**它变 true 的那一刻**开始计时。

## 八、第三轮（2026-10-09 14:0x）：换成 DSH **官方注册模式** —— 这才是真根因

上一轮把依赖收窄到 `['tools']`，重启后日志**仍然**是：

```
[apply]  插件开始加载
[inject] 准备注册 root.inject([tools])（sessionProjections 已改为可选）
         ← 还是没有 [host]！
```

⇒ **`root.inject` 这个机制本身在本机 DSH 上不可靠**，不是"依赖是哪一个"的问题。

### 对照两个正常工作的一线插件，找到了正确写法

```js
// @liustack/modlens/dsh/index.js
export const name = 'modlens'
export const inject = ['tools', 'agents', 'attachments', 'llm']   // ← 模块级声明
export function apply(ctx, config = {}) {
  ctx.tools.register(readImageTool(preferred))                    // ← 直接注册
}
```

```js
// dsh-univer-office/lib/index.js
var inject2 = ['univer', 'tools']
function apply4(ctx, config) {
  ctx.tools.register(withUniverErrorContent(newTool(ctx, ...)))   // ← 直接注册
}
```

**机制**：`export const inject` 是**声明** —— DSH 会**等这些服务就绪后才调用 `apply`**，
而 `apply` 的 `ctx` 上**直接就有 `tools`**，**根本不需要再 inject 一次**。
（必需服务靠 export 声明；**可选**服务如 `webServer` 才用 `ctx.inject` 等它出现。）

### 改法（三处）

1. 加 `export const inject = ['tools']`；
2. `apply` 里 `root.inject(['tools'], (ctx) => { …1000 行… })` → **立即执行** `;((ctx) => { …1000 行… })(root)`；
3. 模块导出确认：`name = 'qwen-paint'`、`inject = ['tools']`。

### A/B 对照（`scripts/_init_abort_test.mjs`）

| | 修复前（`root.inject`） | 修复后（官方模式） |
|---|---|---|
| `inject` 声明 | ❌ 无 | ✅ `["tools"]` |
| 已注册工具 | **(无)** | draw_image, list_available_models, check_acceleration |
| 走到状态端点注册 | ❌ **否** | ✅ **是** |

**并且**：mock 里故意不提供 `ctx.on`，初始化**照样走完**（step 保护生效），
只在日志里留一行 `[init] hook.tools-result 失败：ctx.on is not a function` —— 不再掐死后面。

### 顺带（按主人 2026-10-09 的补充要求核实）

- **加速包只带下载器、不预塞文件**：`ACCEL_PACKS` 全是 `kind:'pip'` + `repo:` 元数据；
  `assets/` 里只有一张 `loading.webp`，没有任何已下载的加速包。
- **A / N / I × Windows / Linux 分得很清**：
  - AMD 一支**刻意留空**（沿用通用链 + `quad`，不引第三方内核；仅 RDNA4 换启动参数）
  - NVIDIA → `sageattention` / `nunchaku`（+ Windows 专用 `triton-windows`）
  - Intel → `ipex`
  - **平台独占**：`triton-windows` 只给 `win32`、`triton` 只给 `linux` —— 装错会顶掉正确的那个

  光晕改双层 drop-shadow。

## 九、**第四轮（终结真凶）**：`ctx` 是 Proxy —— 我自己加的诊断代码把插件打成了「异常」

### 症状（主人截图）

插件管理器里显示：

```
dsh-qwen-paint
【(绘图)千问 · @奇迹与你】让 DeepSeek Harness 在对话里直接调用本机 ComfyUI…
qwen-paint
异常          ← 不是"已停用"，是 **fiber FAILED**
```

日志则停在：

```
2026-10-09T06:09:48.363Z [apply]  插件开始加载 pid=7688
2026-10-09T06:09:48.363Z [inject] 准备注册 root.inject([tools])（…）
                                  ← 再没有任何一行，连 [host] 都没有
```

### 怎么定位的（这次换了方法：**不猜，用真宿主跑**）

前几轮所有测试都是**自己写的 mock** —— 而 mock 永远不可能是 cordis 本身。
于是这次直接**从 DSH 的 `resources/app.asar` 里把 `@deepseek-ai/cordis` 解出来**，
用**真 cordis** 起 root ctx、provide 一个假 tools、`root.plugin(mod, {})` 加载真插件。

**一次就抓到了**：

```
fiber.state = 3 (FAILED)
fiber._error = Error: cannot get property "webServer" without inject
    at lib/index.js:3725:60          ← 指向那一行诊断
```

### 根因

cordis 的 `ctx` 是 **Proxy**（`cordis/lib/index.js` → `ReflectService.handler.get`，第 673 行）：

```js
get: (target, prop, ctx) => {
  if (isSpecialProperty(prop)) return Reflect.get(target, prop, ctx)
  if (Reflect.has(target, prop)) return getTraceable(ctx, Reflect.get(target, prop, ctx))
  const error = new Error(`cannot get property "${prop}" without inject`)   // ← 第 676 行
  …
  throw enhanceError(error)
}
```

**只有这些是"安全属性"**（由 `this.mixin(...)` 混入，第 736–753 行）：

| 来源 | 属性 |
|---|---|
| reflect | `get` `set` `provide` `accessor` `mixin` |
| fiber | `runtime` `effect` |
| registry | `inject` `plugin` |
| events | `on` `once` `parallel` `emit` `serial` `bail` `waterfall` |

**其余一律是"服务"**，读一个没写在 `inject` 里、当前也没就绪的服务 → **直接抛错**。

而我在**上一轮**为了"终结猜测"加的宿主能力快照：

```js
diag('host', `ctx API：… webServer=${typeof ctx?.webServer} …`)
```

**`typeof ctx?.webServer` 不是安全的存在性检查，它就是"去读 webServer"** ⇒ 抛错
⇒ `apply` 抛错 ⇒ fiber `FAILED` ⇒
**工具一个没注册、状态端点根本没注册** ⇒ 界面卡在「正在启动中」。

**我为了排查问题写的代码，成了问题本身。** 这是本轮最该记住的教训。

### 修复

**① 新增 `safePeek()` 工具函数**（`lib/index.js`），封装"探测可选服务"的正确姿势：

```js
function safePeek(read) {
  try {
    const v = read()
    return v === undefined ? 'absent' : typeof v
  } catch {
    return 'absent'          // 抛错 = 该服务当前不可用
  }
}
```

**② 三处裸读全部改为安全写法**：

| 位置 | 原来（会抛） | 现在 |
|---|---|---|
| `diag('host', …)` | `typeof ctx?.webServer` | `safePeek(() => ctx?.webServer)` |
| 状态端点·无 inject 分支 | `ctx?.webServer ? '有' : '无'` | `safePeek(() => ctx?.webServer)` |
| 状态端点·准备注册 | `ctx?.webServer ? '有' : '无'` | `safePeek(() => ctx?.webServer)` |
| `onProduced` 取 turn | `ctx?.sessionProjections ?? ctx?.get?.(…)` | `ctx?.get?.('sessionProjections')`（见下） |

> 最后一条特别隐蔽：`??` 左侧一抛错就**跳进 catch**，右侧 `ctx.get` **永远没机会执行** ——
> 等于这个服务永远取不到。必须**先走安全的 `ctx.get`**。

**③ 正确姿势速查**：

```js
// ✅ 探测"服务在不在"
const svc = ctx.get?.('webServer')        // 不存在 → undefined，不抛错

// ✅ 必需服务 → 写进模块级 inject，然后用 ctx.xxx
export const inject = ['tools']
ctx.tools.register(...)

// ✅ 可选服务 → 用 ctx.inject 等它出现
ctx.inject(['webServer'], (webCtx) => { … })

// ❌ 绝对不要
typeof ctx?.webServer                     // = 读它 = 可能抛错
ctx?.someOptionalService                  // 同上
```

### 验证（**真宿主，不是 mock**）

| | 修复前 | 修复后 |
|---|---|---|
| `fiber.state` | **3 (FAILED)** ❌ | **2 (ACTIVE)** ✅ |
| `fiber._error` | `cannot get property "webServer" without inject` | **(无)** |
| 已注册工具 | **(无)** | draw_image, list_available_models, check_acceleration |

### 新增自测：`scripts/_cordis_proxy_test.mjs`（**第六套**）

**这是本轮最重要的产出**。它做两件事：

1. **用真 cordis 加载真插件**（复用从 `app.asar` 解出的 `_vendor/`），断言
   `fiber.state === ACTIVE`、`_error` 为空、三个工具都注册上、无未处理 rejection。
2. **静态扫描源码**：禁止出现 `ctx?.webServer` / `ctx?.sessionProjections` 一类
   "裸读未声明服务属性"（`safePeek(...)` 包住或写在 `ctx.inject([...])` 参数里才放行）。

`_vendor/` 不存在时**自动降级**为只跑静态扫描（它体积大、不打进发布包），
并如实说明"跳过了真机复现"——**不静默跳过**。

六套自测现状：

```
_adapt_test          === 全部通过 ===
_intent_test         === 全部通过 ===
_opt_status_test     === 全部通过 ===
_portability_test    === 全部通过 ===
_init_abort_test     === 通过 ===
_cordis_proxy_test   === 通过（11 项）
```

### 教训固化（写进项目铁律）

> **cordis 的 `ctx` 是 Proxy。服务属性只有写进 `export const inject` 才能裸读；
> 探测可选服务只能走 `ctx.get(name)` 或包在 try 里。
> `typeof ctx?.xxx` 不是安全检查，是"读属性"，会抛错并直接判插件 FAILED。**
>
> 推论：**任何"为了排查而加的诊断代码"，本身必须是最不可能出错的代码。**
> 诊断读宿主状态时，一律走 try 包住的安全探测。

## 十、**第五轮（2026-10-09 14:4x）**：尺寸校验假报警 + 比例被静默吞掉

这一轮的触发是主人一句 **「去给我画一个青苹果」** —— 一次最普通的出图，
却把两个互相纠缠的 bug 一起炸了出来。

### 10.1 报错现场

```
画图失败：Error: ComfyUI 出的图尺寸不对：请求 992x992，实际 1024x1024。
本次文件名：dsh-qwen-paint_00006_.png
```

**诡异点**：提示说"实际 1024x1024"，可任务是真的出图成功了、文件也落盘了。
出图没坏，坏的是**校验逻辑**。

### 10.2 根因：`buildWorkflow` 内部归一了尺寸，却没告诉调用方

`buildWorkflow` 是**纯函数**，它的返回值**就是**发给 ComfyUI 的 prompt 载荷
（直接 `JSON.stringify` 后 POST），所以**结构不能动**。

问题在于：它内部把调用方请求的 `3:4 / 992x992` 按"优化档"归一成了 `1024x1024`，
**但归一结果只活在这个函数里，没有回传给调用方**。

于是调用方拿着**自己当初请求的 992x992** 去比对**实际输出的 1024x1024**，
必然不等 → 抛"尺寸不对"。

> **这是一类通用陷阱**：纯函数内部做了"策略改写"，却只 return 数据、不 return 元信息。
> 调用方看不见改写，就会拿旧假设去校验新结果。

### 10.3 修法：让纯函数把"生效尺寸"一并交出来

不能改返回值的结构（那是协议载荷），所以用**不可枚举属性**挂元信息 ——
`Object.keys` 看不见、`JSON.stringify` 也不序列化，ComfyUI 完全无感：

```js
Object.defineProperty(workflow, '__effective', {
  value: Object.freeze({ width: effWidth, height: effHeight, locked: !withRef && lockSize }),
  enumerable: false,   // ← 关键：不进 JSON、不进 Object.keys
  writable: false,
  configurable: false,
})
return workflow
```

调用方三处全部改用**生效尺寸**：

| 位置 | 改前 | 改后 |
|---|---|---|
| 校验 ComfyUI 出图 | 比对 `width/height`（请求值） | 比对 `outWidth/outHeight`（生效值） |
| 落盘文件名 | 请求尺寸 | 生效尺寸 |
| 返回值 | `width/height` | `outWidth/outHeight` |

另外加 `requestedWidth/requestedHeight` —— **只在确实发生归一时才带**，
让返回值既能溯源，又不会冗余。

### 10.4 顺带揭出的真问题：**7 个比例全被吞掉**

修 bug 时顺手实测了全部比例，结果很难看 —— 尺寸锁开着时：

| 比例 | 1.0MP 应出 | 锁档实际 |
|---|---|---|
| 1:1 | 992x992 | 1024x1024 |
| 3:4 | 864x1152 | **1024x1024** |
| 4:3 | 1152x864 | **1024x1024** |
| 2:3 | 832x1216 | **1024x1024** |
| 3:2 | 1216x832 | **1024x1024** |
| 16:9 | 1344x736 | **1024x1024** |
| 9:16 | 736x1344 | **1024x1024** |

**七个塌七个** —— 界面上"选比例"这个功能，实质上一直是个摆设。
这是我当初为省那点算力加尺寸锁埋的坑：**用功能阉割换速度，还把它默认打开了。**

### 10.5 主人决策：**完全听调用方**

主人选了「完全听调用方」。落地：

| 键 | 改前 | 改后 | 理由 |
|---|---|---|---|
| `forceOptimizedSize` | `true` | **`false`** | 比例是功能，不能为了提速吞掉 |
| `forceTurbo8Steps` | `true` | `true`（保留） | 纯提速，不改画面内容与构图 |

改动落在两处：`lib/index.js` 的 `DEFAULTS` 与 `cordis.patch.yml` 的 `config` 段。

## 十一、**第六轮（2026-10-09 15:0x）**：通用性三个真 bug + 优化界面升级为四态

主人的原话：「再看一下有什么bug，还可以修特别是通用性，还有这里那个启用优化的，
你点进去怎么还是那个界面选择的界面，你启用优化就应该是启用了哪些优化，
这个也肯定要用区分啊你点进去就应该是告诉你启用了哪些优化，
哪些可以启用哪些没启用，哪些不能启用」。

这一轮分两半：**A 组通用性 bug**（我该负责的），**B 组优化界面**（主人要的）。

### 11.1 A 组：三个"Windows 上正常、Linux 必崩"的 bug

这一轮所有 bug 都属于同一类：**开发机是 Windows，所以永远不会自己暴露**。

#### A1 ☆ 加速包探测写死了 PowerShell 语法（未分平台）

`probeAccelPack` 里探测"某个 pip 包装没装"的那行：

```js
const out = await runShell(
  `& '${env.py...}' -c "import ${pack.pythonModule}" 2>&1 | Out-Null; `
  + "if ($LASTEXITCODE -eq 0) { 'YES' } else { 'NO' }",
```

`&`、`Out-Null`、`$LASTEXITCODE` **全是 PowerShell 专有语法**，而这行没有平台分支。
`runShell` 在非 Windows 上走 `sh -c` —— `&` 是 shell 的**后台运算符**，
整条命令语法错 → 被 `catch` 吞掉 → **恒返回 false**。

后果不止"显示未安装"：`autoSetupAcceleration` 会据此**反复尝试重装**，
每次都失败。用户看到的是"明明装了却一直说没装，还不停重试"。

**最刺眼的是**：`runShell` 自己的注释里就写着
「任何绕过它写 Windows 专有命令都会在 Linux 上直接崩掉」——
**我在别处都写对了，唯独这一行漏了。**

修法：按 `IS_WINDOWS` 分叉。POSIX 分支用 `>/dev/null 2>&1` + 退出码，
路径按 POSIX 规则转义（`'\''`），避免带空格的路径被拆成两个参数。

#### A2 ☆ 诊断日志硬拼 Desktop，绕过了刚做好的跨平台逻辑

```js
return path.join(home, 'Desktop', '千问1生图', 'qwen-paint-diag.log')
```

同一个文件里 `defaultOutputDir()` 做得相当讲究（XDG → Desktop → 桌面 → 主目录，
且注释明确写了 Linux 上 `~/Desktop` 常常不存在、**不许硬造 Desktop**）。
可诊断日志这条路径没走它，直接硬拼 —— Linux 上会造出一个空的 `Desktop` 目录。

修法：`path.join(defaultOutputDir(), 'qwen-paint-diag.log')`，顺带复用了那套探测。

#### A3 扫描器硬编码六个盘符

```js
"$cands += 'X:\ComfyUI','X:\ComfyUI','X:\ComfyUI','X:\ComfyUI','X:\ComfyUI','X:\ComfyUI'"
```

装在第 7 个盘（H:/I:…）或改过盘符就覆盖不到；虽有 `Get-PSDrive` 兜底，
但兜底只找**目录名含 comfy** 的，"盘符不在表里 + 自定义命名"仍会漏。

修法：改成 `foreach ($l in [char[]](65..90))` **动态枚举 A–Z**，
一个盘符都不预设，仍保留 `X:\ComfyUI` / `X:\ComfyUI_windows_portable` 的快路径。

**真机实测**（渲染出脚本后真跑）：正确命中
`X:\ComfyUI\venv\Scripts\python.exe|X:\ComfyUI\main.py|X:\ComfyUI`。

### 11.2 B 组：优化界面 —— 一个比主人描述更严重的发现

#### 先说那个"更严重"的

主人说"点进去还是那个界面"。查下来发现：

> **`full` 态（优化全启用）时，徽标的 `clickable` 是 `false` —— 根本点不开。**

也就是说，**优化状态最好的时候，恰恰是最看不到细节的时候**。
而设置菜单里当时只有「后端 / 自动关闭 / 生图判断 / 外观」四组，
**压根没有「优化」入口** —— 用户想找优化自然会去菜单里翻，翻不到就以为没这功能，
点了别的东西（于是看到的是"选择界面"，跟他想看的不是一回事）。

两个问题叠在一起，就是主人感受到的那个体验。

#### 真正的信息缺口：三种"没启用"被糊成了一句

`detail` 原先只有 `on: true/false` 二元。但 `whyOff` 里其实混着**三种完全不同的处境**：

| 原话（whyOff） | 真实处境 | 用户该做什么 |
|---|---|---|
| 没装 TE-Speed 节点 | 缺外部组件 | **装上就能快** —— 值得动手 |
| 被配置关了（teSpeedEnabled=false） | 配置关的 | **改一行配置就能快** —— 最容易修 |
| 依赖 turbo8 链路，turbo8 没生效 | 上游没通 | **现在做什么都没用** |

三者显示成同一句灰字，等于把"能做的"和"做不了的"糊在一起 ——
用户要么白折腾、要么以为插件坏了。**主人要的正是这个区分。**

#### 四态落地

host 侧每项新增两个字段：

- **`state`**：`on`（已启用）/ `available`（可启用·缺件）/ `off`（可启用·配置关了）
  / `blocked`（不可启用·依赖或平台）。UI 直接照它上色，**不再从文案里猜**。
- **`action`**：一句话"该做什么"。没有可做之事时给空串，UI 不渲染那一行。

另加 **`stats`**（四态计数），summary 也从"缺了哪几项"改为
**"还差 N 项可启用"** 或 **"N 项当前不可启用"** —— 一眼看清分布。

界面侧：

| 改动 | 说明 |
|---|---|
| 徽标 `full` 改为可点 | 任何状态都能看明细 |
| 面板加"总账"行 | `共 4 项：3 项已启用 · 1 项可启用` |
| 面板四态渲染 | 每项 = 字形 + 名称 + 状态词，下面缩进一行 `→ 该做什么` |
| 菜单新增「优化」组 | 与「后端 / 自动关闭 / 生图判断」并列，点它弹**同一个**面板 |
| 菜单项文字报分布 | `优化状态：3/4 已启用 · 1 可启用` —— 不必点进去才知道 |
| 无数据时有提示 | 点了还没拉到数据 → 2.6 秒轻提示，不是"点了没反应" |

**一个刻意的设计**：菜单**不自己造面板**，而是复用徽标的 `openDetail()`。
两套渲染必然逐渐走样，用户看到"徽标点开"和"菜单点开"不一样 —— 那是最糟的一类 bug。
所以是**单一数据源、单一渲染路径**。

#### 顺手堵住的一个假报告

`probeFailed`（探测失败）时，`resolvePlan` 会按"能力齐全"假设走，
于是四项 state 全算成 `on`。**直接显示就是假报告** —— 用户会以为加速都生效了。
现在整批改写成 `unknown`，且 `action` 统一为"等 ComfyUI 起来后重新检测"。

#### 无障碍：字形与颜色双通道

四态不止用颜色区分，**各自还有独立字形**（`✓` / `✕` / `?`）——
色觉障碍用户也要能分辨。只靠颜色传达状态是不合格的。

### 11.4 教训固化

> **一类最隐蔽的 bug：Windows 上永远正常、Linux 上必然出错。**
> 开发机是什么系统，就会系统性漏测另一种。
> 判据很简单：**凡是往 shell 里塞的字符串，先问"这在 sh 里是什么"。**
> `runShell` 之所以叫 runShell 而不是 runPowerShell，就是为了这个 ——
> 它不是"顺便支持多平台"，它是**所有系统命令的唯一出口**。
>
> **"缺件"和"做不了"必须分开说。**
> 把"你装个东西就能变快"和"你这儿根本用不了"显示成同一句灰字，
> 用户不是在读状态，是在猜谜。
>
> **纯函数/单一数据源的价值在界面侧同样成立。**
> 同一个状态有两个入口时，别写两套渲染 —— 迟早走样，
> 而且用户会以为是"时好时坏"。
