## 一、先更正两个前提

### 1.1 「11.67 s」是测量假象

原报告里的 11.67 s 是同 seed 命中 ComfyUI 直接输出缓存的结果。本次用**毫秒级内部时间戳**（`status.messages` 的 `execution_start` → `execution_success`）重新测量，三轮取稳态：

|                  | 耗时           |
| ---------------- | ------------ |
| turbo8 8 步（无 TE） | **11.581 s** |
| turbo8 8 步 + TE  | **9.431 s**  |

TE 的真实增量是 **−18.6%（1.23×）**，不是 −43%。

### 1.2 ZLUDA / TunableOp 不适用（结论：出局）

- 本机是 **原生 ROCm**（`PyTorch 2.9.1+rocm7.2.1`，`gfx1100`），不是 ZLUDA 转译路线。
- ZLUDA 的作用是给**没有原生支持**的卡做 CUDA 转译；已有原生 ROCm 时套用只会更慢。
- TunableOp 是 **cuBLASLt（CUDA）** 的特性，ROCm/HIP 后端没有这条代码路径。

→ **两条都无需 A/B，直接划掉。**

## 二、实测结果总表

测量协议：6 臂 × 3 轮，**每次换 seed**（防输出缓存），丢弃第 1 轮冷启动，取后 2 轮均值。计时用 ComfyUI 内部毫秒时间戳。

| 方案                      |        稳态耗时 |       加速比 |       相对基线 |
| ----------------------- | ----------: | --------: | ---------: |
| A0 baseline（turbo8 8步）  |    11.581 s |     1.00× |          — |
| A1 + TE-Speed           |     9.431 s |     1.23× |     +18.6% |
| A2 + QwenImage21Speedup |    10.711 s |     1.08× |      +7.5% |
| **A3 + TE + Speedup**   | **8.639 s** | **1.34×** | **+25.4%** |
| A4 + T8 BlockCache      |     9.712 s |     1.19× |     +16.1% |
| A6 + T8 Spectrum        |     9.664 s |     1.20× |     +16.6% |
| A5 + TE + T8 Block      |    **无法运行** |         — |        硬冲突 |

**当前最优可叠组合：TE + Speedup = 8.639 s。**

## 三、跳步机制实测（关键，解释一切）

三个缓存方案在 8 步下的实际跳步能力，全部由各自日志量化：

| 方案          | 8 步实际跳步          | 日志原文                                                                    |
| ----------- | ---------------- | ----------------------------------------------------------------------- |
| TE-Speed    | **0 / 8（0%）**    | `Qwen TE predictor: predicted 0/8 steps (0.0% model-call acceleration)` |
| Speedup     | **1 / 8（12.5%）** | `1 cached of 8 model forwards (12.5% skipped)`                          |
| T8 Block    | **2 / 6**        | `T8: full=6 cache=2`                                                    |
| T8 Spectrum | **2 / 6**        | `T8: full=6 cache=0 spectrum=2`                                         |

### 3.1 TE 从不跳步，但仍在加速

TE 的每一步日志都是 `eligible=0/1`、`result=latent_change`。8 步的 t 序列为  
`1.000 / 0.933 / 0.857 / 0.769 / 0.667 / 0.546 / 0.400 / 0.222`，  
各步 `change` 在 0.087–0.318 之间，**全部高于阈值 0.06**。且 TE 内部 window 硬编码 `0.18–0.86`（实际 t≤0.82），前 3 步直接排除。

TE 的 −18.6% 来自 **算子层** 的 KV/attention 复用（`batch_offset=1`），不是跳步。这是实打实的收益，但**不会随步数减少而线性放大**。

### 3.2 Speedup 的标定前提在 8 步下完全失效（它自己的日志打了自己）

```
QwenImage21Speedup: 1 cached of 8 model forwards (12.5% skipped)
QwenImage21Speedup: per-step indicator drift mean 0.4088, max 0.7426 over 7 steps
  (a useful cache_threshold must exceed the mean; current 0.300)
QwenImage21Speedup: replayed-residual error vs actual forward mean 0.1289
  (target_error = 0.05 → 超标 2.6 倍)
```

它的标定假设是 40 步下每步 drift ≈ 0.13；**实测 8 步下 drift = 0.409，是设计点的 3 倍。** 阈值 0.30 压不住，一路强制完整前向。这就是它宣称 ~50% 跳步、实测只有 12.5% 的原因。

**→ Speedup 必须按 40 步 / ≥2.2 MP 使用才有意义。在 8 步下它只有 +7.5%。**

## 四、硬冲突实测（不是推测）

**TE + T8 BlockCache 无法共存**，服务器实测抛错：

```
ValueError: Qwen Image 2.1 T8 cache requires exclusive diffusion-wrapper ownership;
use T8 Spectrum
  at Comfyui-Qwen-Image-2.1-BlockCache-T8/runtime.py:51 in validate_model
```

**根因**：TE-Speed 的 `te_predictor` 模式**也挂了 `DIFFUSION_MODEL` wrapper**，日志末行可见 `Qwen TE predictor calls: diffusion_wrapper=8`。而 T8 在 `validate_model()` 中要求对 diffusion wrapper 的**独占所有权**，检测到外部 wrapper 即抛错。

### 静态冲突矩阵

|              | TE-Speed                                                              | Speedup                                 | T8 Block                                |
| ------------ | --------------------------------------------------------------------- | --------------------------------------- | --------------------------------------- |
| 挂载方式         | monkey-patch `PoseBranchCache.select`（attention 层）+ diffusion wrapper | `add_wrapper_with_key(DIFFUSION_MODEL)` | `add_wrapper_with_key(DIFFUSION_MODEL)` |
| **TE-Speed** | —                                                                     | ✅ 可叠（已实测）                               | ❌ 硬冲突（已实测）                              |
| **Speedup**  | ✅                                                                     | —                                       | ❌ 互斥（同挂载点）                              |

## 6.5 Spectrum 的彻底结论（本轮新增）

之前把它归类为"与 TE 同层互斥"是**错的**。真相：**Spectrum 写在旧版 Qwen-Image 架构上，对 2.1 完全不兼容。**

两个根因，全部定位并绕过：

1. **`txt_norm` 缺失** —— `resolve_qwen_core()` 要求核心具备 7 个字段，2.1 把 `txt_norm`  
   挪进了 `txt_in.text_norm`，顶层没有。补 property 别名后 `is_qwen_like_core` 由 False 翻 True。
2. **ROCm 无 MAGMA** —— `chebyshev.py:105` 对 GPU 小矩阵调 `torch.linalg.cholesky` 报错。  
   改 CPU float64 求解（4×4，开销可忽略）。

已做诊断兼容层 `custom_nodes/_spectrum_qwen21_compat/`（纯运行时补丁，不碰上游文件，删除即复原）。  
**绕过成功，Spectrum 能跑了**，但：

| 指标                             |                                       结果 |
| ------------------------------ | ---------------------------------------: |
| `actual_calls`                 |                                **8 / 8** |
| `forecast_calls`               |                                    **0** |
| 标记 forecast 的第 6、7 步耗时         | 1.70 / 1.71 s/it（**比 warmup 的 1.42 还慢**） |
| 最裸链（UNET→Spectrum→KSampler）总耗时 |                20.13 s（baseline 11.58 s） |

**预算模型对不上 8 步**：前 2 步 warmup、第 3~5 步 `insufficient_history`（`history_points=5`）、  
末步 tail，全部强制 real；只剩第 6、7 步可预测，而那两步没省下任何计算。

**→ 它是为 40 步长链设计的。8 步下纯负收益，兼容层仅留作诊断，不建议启用。**

## 七、4 步蒸馏为什么不建议

现有 Turbo8 是 rank-128 步蒸馏 LoRA，227 层无缝映射，官方给了完整指标（PickScore 22.15→21.94，OCR 精确匹配 95%→75%，DINOv2 编辑相似度 0.967）。**它是可量化、可信任的。**

三个 4 步候选各有硬伤：

- **lightx2v**：工作流用标准 KSampler（这点比 Fun-Acc 干净），但**全部是 Qwen-Image 1.0 / Edit 2509**，LoRA 文件 `Qwen-Image-Lightning-4steps-V1.0.safetensors` 不针对 2.1。
- **Fun-Acc（阿里 PAI）**：需自定义 sigma `1.0, 0.9169867, 0.7861579, 0.549491, 0.0` + 非 LoRA 的 `norm_q`/`norm_k`/`text_norm` 参数；无官方 ComfyUI 路径（仅 kijai 实验分支）；官方承认密集小字退化。
- **Pruna 5/8 步**：每档绑定自己的 sigma 表；必须 `ManualSigmas` + `SamplerCustom`；alpha=128 写在 safetensors metadata 里 ComfyUI 的 LoRA loader 不读；**仅在 1K 分辨率训练**；自评质量低于 40 步底模。

**换 4 步的代价**：放弃官方支持、手搓调度、接受未知退化。**收益**（如果用 lightx2v 那档）大约再快 2–3 s。

## 八、当前推荐

- **默认保持现状**：turbo8 8 步 + TE，稳态 9.431 s。

- FlashVSR（视频）
- TAESD（画质不可用 + 无千问版）
- T8 Spectrum（画质退化）

- **VOSR2 超分**：出图后 1MP→2K/4K，与现有全链正交。权重 6.97 GB，纯 Python 可审计。
  - 注意：训练上限 512 px，输出 >512 必须 `tile_size=512`；>1024 再加 `vae_tile_size=1024`。

### 已知未测 / 不确定项（如实列出）

- T8 Block 在**画质敏感场景**（人脸、文字）的锐度损失是否有感知影响 —— 本次仅测了静物茶壶。

## 九、测量规范（本轮教训）

1. **每次计时必须换 seed** —— 同 seed 会命中 ComfyUI 直接输出缓存，把 20 s 变成 0.4 s。
2. **计时要取 ComfyUI 内部毫秒时间戳**（`status.messages`），不要用 HTTP 轮询（1 秒粒度会把结果量化成 `11.02/12.02` 这类假精度）。
3. **丢弃首轮冷启动** —— 模型加载会让 baseline 出现 12.8 s vs 24.0 s 的巨大抖动。
4. **下载文件大小以服务器权威值为准** —— VOSR2 权重必须比对 HF 的 `X-Linked-Size`，不要用记忆中的估算值。

### 11.3 为什么 RDNA3 节点「日志说启用了」却是 0 收益 —— 计数器取证

内核级基准（**干净 GPU**，Qwen-Image-2.1 真实形状 32 头 × 128 维，MMDiT 联合注意力）：

| 形状                    | PyTorch SDPA | fa_rdna3 |        加速 |
| --------------------- | -----------: | -------: | --------: |
| 1024² 联合 S=4352（fp16） |     16.25 ms |  5.35 ms | **3.04×** |
| 1024² 联合 S=4608（fp16） |     17.87 ms |  5.78 ms | **3.09×** |
| 1024² 纯图 S=4096（fp16） |     13.99 ms |  4.84 ms | **2.89×** |
| 1024² 联合 S=4352（bf16） |     16.04 ms |  9.81 ms | **1.64×** |

内核快 3 倍，端到端却 0 收益。装了调用计数器（`custom_nodes\zz_fa_counter`）后拿到实锤：

```
[INFO] Composing RDNA3 Flash Attention under an existing attention override
[INFO] Enabled RDNA3 Flash Attention for the patched ComfyUI model
[FA-COUNTER] state=已挂载到 ...RDNA3-Flash-Attention\fa_rdna3\comfyui.py
            | flash_attention 0 次 | 回退 0 次
```

**两个计数都是 0** —— 说明 `optimized_attention_override` 这条链**一次都没被调用**。  
原因：日志里的 "Composing ... under an existing attention override" 表明  
`QwenImage21Cache`（comfy-kitchen INT8）已经先装了一个 attention override，  
而它**不向下委托**给传入的嵌套函数，于是 RDNA3 整条链被架空。

> 这正是你第 4 条「验证而非盲开」的价值：如果只看 `Enabled RDNA3 Flash Attention`  
> 这行日志就下结论，会误报一个 3× 的收益。

#### 11.7.1 端到端实测（2026-10-09 完成）

**打通的关键阻塞**：Qwen-Image VAE 解码输出是 **4 通道 RGBA**，而 `VOSR2Upscale`

**测试方法**：默认加速链（Turbo8 8步 + TE-Speed + QwenImage21Speedup + quad 注意力），

### 11.8 本轮新增的测量教训

1. **测 GPU 时先确认没有别的进程在抢卡** —— 第一版 fa_rdna3 基准跑出 0.61×/0.48× 的负数，  
   全是因为 TunableOp 的 ComfyUI 还在同一块 GPU 上跑；清干净后同一份代码变成 2.9×~3.1×。
2. **确认端口上只有一个 ComfyUI** —— 出现过两个实例并存（`--port 8188` 被旧实例占着），  
   新实例没绑上，测出来的数据全是假的。跑 A/B 前先按 PID 列进程核对。
3. **「日志说启用了」不等于「内核在跑」** —— 必须装计数器取到「调用 N 次」才能下结论。
4. **输出逐位相同的两个配置，不可能有真实性能差** —— PSNR 99 dB / MAD 0.000 是戳穿  
   「假收益」最快的判據。
